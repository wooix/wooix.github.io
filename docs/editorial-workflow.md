# Daily(일일) 편집 운영 계획

현재 상태는 **planned(계획됨)**입니다. 사이트와 초기 글은 정적 콘텐츠이며, 이 문서와 `editorial.config.json`은 향후 연결할 편집 절차를 정의합니다. 예약 작업, 요약 수신 채널, 사용자 응답 조회, 영속 상태 저장은 아직 이 설정만으로 실행되지 않습니다.

## 하루의 흐름

기준 시간대는 **Asia/Seoul(한국 표준시)**입니다.

| 시점 | 의도한 동작 | 남길 기록 |
| --- | --- | --- |
| 07:00 | 관심 분야의 검증된 자료 5–7개를 요약해 전달 | 날짜별 요약, 출처, 순위 근거, 실제 전달 시각 |
| 사용자 응답 후 | 선택한 항목을 읽기 편한 블로그 글로 작성 | 선택 항목과 수신 시각, 초안과 검증 결과 |
| 12:00 | 그날 요약에 **응답이 전혀 없을 때만** 최우선 이슈 한 건을 발행 | 무응답 조회 결과, 선택 이유, 발행 URL |

“조금 뒤에 볼게”, 질문, 다른 주제 요청도 응답입니다. 항목 번호를 고르지 않았다는 이유로 무응답으로 처리하지 않습니다. 애매한 응답이면 자동 선택을 보류하고 의미를 확인합니다. 이미 선택된 글이나 발행된 글이 있는 날에는 12:00 작업이 별도의 글을 추가하지 않습니다. 사용자가 명시적으로 여러 글을 요청한 경우는 그 요청을 별도로 기록합니다.

사용자의 선택은 현재 대화에서 받을 수 있으며, 상시 운영할 별도 채널과 실행 환경은 아직 미정입니다. 응답을 읽을 수 없거나 조회가 실패한 날에는 “응답 없음”을 추정하지 않습니다.

## 조사와 요약

Primary Source(1차 출처)는 논문 원문, 저자 저장소, 연구그룹의 공식 블로그·기술 보고서입니다. 인기 목록은 후보 발견에 참고할 수 있지만 사실 확인의 대체물로 사용하지 않습니다.

각 항목은 제목, 짧은 요약, 관심 분야와의 연결, 무엇이 새로워졌는지, 증거의 한계, 원문 링크를 갖습니다. 최초 공개일·수정일·확인일을 따로 보관합니다. 확인한 자료가 다섯 개에 못 미치면 부족한 이유를 밝히며 숫자를 맞추기 위해 자료를 만들지 않습니다.

07:00 요약 예시 형식:

```text
날짜 · 확인 범위 · 실제 전달 시각
1. 원 제목 — topic
   요약: 핵심 변화와 방법을 2–3문장으로 설명
   읽을 이유: 현재 관심사와의 연결
   근거·한계: 검토한 실험 범위와 확인하지 못한 부분
   출처: 원문 링크 · 원 공개일 · 검토 버전
```

최신 소식과 Milestone Paper(이정표 논문)는 구분해 표시합니다. 첫 버전의 DPO·CAA·AWQ·지식 증류 글은 기초 읽기 자료이고, FInject 가이드는 공개 문헌을 연결하는 연구 노트입니다.

## 최우선 이슈를 고르는 기준

관심사 관련성 40점, 근거의 질 30점, 예상 영향 20점, 시의성 10점의 편집 기준을 사용합니다. 점수와 이유를 함께 남깁니다. 이는 전 세계에서 가장 인기 있는 논문을 객관적으로 측정했다는 뜻이 아닙니다.

동점이면 근거의 질, 원 공개 시각, 원문 URL 순으로 결정해 재실행 시 결과를 안정적으로 유지합니다. 같은 논문의 arXiv 버전, 연구그룹 블로그, 저장소 소개는 동일한 사건인지 확인해 중복 제거합니다. 검증이 충분한 후보가 없으면 그날 발행을 보류하고 사유를 기록합니다.

## 상태와 중복 방지

실제 응답 내용과 운영 기록은 공개 저장소 밖의 영속 저장소 또는 git에서 제외한 `.editorial/`에 둡니다. 아래 경로는 **설계된 저장 위치**이며 실제 일일 실행 기록이 생성되었다는 뜻은 아닙니다.

- `.editorial/digests/YYYY-MM-DD.json`: 후보, 검증 출처, 순위, 전달 결과.
- `.editorial/state/YYYY-MM-DD.json`: 요약 전달 여부, 응답 여부, 선택·발행 상태.
- `docs/editorial-state.example.json`: 값이 비어 있는 공개 상태 예시.

운영 상태는 `pending → digest-sent → selected 또는 fallback-eligible → drafting → validated → published`를 기본 흐름으로 삼습니다. 응답 조회 실패·자료 미확인·빌드 실패는 `deferred`로 기록합니다. `digest-sent`는 실제 전달이 성공한 뒤에만 기록하고, 전달되지 않은 요약을 무응답 자동 발행의 근거로 삼지 않습니다.

발행 직전에 다음 조건을 확인해야 합니다.

1. 당일 키 `localDate:publication`을 원자적으로 점유하고, 이미 발행된 기록과 저장소의 글을 조회합니다.
2. 가장 최근의 사용자 응답을 다시 확인합니다. 12:00 직전 선택이 들어왔으면 자동 선택보다 우선합니다.
3. 검증된 후보 하나를 고정하고 동일 키로 재시도를 이어 갑니다. 실패 후 재실행한다고 새 글을 만들지 않습니다.
4. 글 작성·검증·배포 후 실제 URL과 Git revision(깃 변경 이력)을 기록합니다.
5. 배포 성공 여부가 불명확하면 원격 저장소와 사이트를 먼저 대조합니다. 성공 확인 전에는 `published`로 표시하지 않습니다.

잠금은 갱신 시각과 만료를 가져야 하며, 만료된 잠금을 회수하기 전에도 외부 발행 여부를 확인합니다. 단순 JSON 파일 저장만으로 동시 실행의 원자성이 확보되지는 않습니다. 실제 운영 연결 시 실행 환경에 맞는 잠금과 트랜잭션을 구현하고 검증해야 합니다.

## 글쓰기 계약

프로젝트의 `AGENTS.md`를 따릅니다. **English(한국어)** 순서로 핵심 용어를 반복 표기하며, 약어는 처음에 풀어 씁니다. 논문의 사실·자신의 해석·미실행 제안을 명확히 구분합니다. 제목 아래의 핵심 요약만 읽어도 얻을 내용이 보이게 하고, 본문은 작동 원리·근거·한계·연구 질문으로 연결합니다.

FInject의 공개 기준 자료는 [공개 저장소](https://github.com/pnu-clink/finject)와 [데이터셋](https://huggingface.co/datasets/pnu-clink/finject)입니다. 공개 상태는 Manuscript(논문 원고)·Dataset(데이터셋)으로 기록하며, 확인되지 않은 학회 채택이나 비공개 연구 계획을 글에 넣지 않습니다.

## 운영 연결을 마쳤다고 판단할 조건

예약 실행 환경, 요약 전달 채널, 사용자 응답 수신·조회 방법, 영속 상태와 발행 권한을 연결한 뒤에 상태를 `active`로 바꿉니다. 정상 선택, 무응답, 애매한 응답, 전달 실패, 조회 실패, 12:00 경계의 응답, 재실행·동시 실행을 실제 발행 없는 검증 환경에서 확인해야 합니다. 이 작업 전까지 화면과 문서에는 `planned` 상태를 유지합니다.
