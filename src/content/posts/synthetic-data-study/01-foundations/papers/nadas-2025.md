[논문 원문 열기](https://doi.org/10.1109/ACCESS.2025.3589503)

## 초록

<strong>Large Language Model(대규모 언어 모델, LLM)</strong>로 만드는 <strong>Synthetic Data(합성 데이터)</strong>를 자연어와 코드에서 비교한다. 두 영역 모두 지시와 예제로 데이터를 만들고 결과를 수정할 수 있지만, 코드에서는 실행 결과를 검증 신호로 사용할 수 있다는 차이가 있다.

저자들은 비용·확장성·제어 가능성을 장점으로 보면서도 사실 오류, 실제 데이터와의 차이, 편향을 함께 다룬다. 따라서 이 서베이의 중심은 생성 기능의 소개보다, 생성한 자료를 학습에 쓸 수 있도록 만드는 조건에 있다. [저자 공개 원문 초록](https://arxiv.org/pdf/2503.14023v2#page=1)

## I. 서론

라벨이 부족하거나 수집 비용이 큰 과제에서 LLM이 추가 자료를 만드는 접근을 소개한다. 텍스트와 코드를 함께 다루는 이유는 둘 다 기호적 표현이며 언어 모델로 처리할 수 있는 반면, 코드는 문법과 실행 의미가 더 엄격하다는 데 있다. 이미지·음성까지 같은 깊이로 조사하지는 않는다.

기여는 방법 분류, 텍스트의 경험적 결과, 코드의 경험적 결과, 공통 문제와 완화 전략, 미래 방향의 다섯 갈래다. 이 논문이 하나의 모델을 공통 조건으로 재학습해 방법들의 순위를 정한 것은 아니다. 여러 연구의 결과를 연결하는 서베이이므로, 소개된 개선 폭을 모든 과제의 기대 효과로 읽으면 안 된다.

서론 끝의 절 안내와 실제 본문의 번호에는 불일치가 있다. 읽기 순서는 실제 제목인 IV 배경, V 텍스트, VI 코드, VII 문제점, VIII 미래 방향, IX 결론을 기준으로 삼는다. [저자 공개 원문 §1](https://arxiv.org/pdf/2503.14023v2#page=1)

## II. 관련 연구

### A. 자연어 처리의 합성 데이터

<strong>Natural Language Processing(자연어 처리, NLP)</strong>의 기존 서베이는 전통적 변형부터 신경망과 프롬프트 기반 생성까지 폭넓게 정리하지만, 프로그래밍 코드의 기능 검증은 상대적으로 적게 다룬다고 설명한다. 이 절은 본 논문이 텍스트 연구만으로 충분하지 않다고 판단한 근거를 제시한다.

### B. LLM 기반 합성 데이터 파이프라인

Long et al.의 생성·선별·평가 틀은 전체 과정을 보는 데 유용하지만, 저자들은 텍스트와 코드의 경험적 차이를 더 상세히 비교할 필요가 있다고 본다. 특히 <strong>Execution Feedback(실행 피드백)</strong>을 어떻게 활용하는지가 코드 영역의 추가 논점이다.

### C. 합성 코드 데이터 서베이

코드 관련 서베이는 모델 능력·성능 평가 또는 지시 데이터·번역·수정 방법에 집중한다. 저자들은 이런 연구만 따로 읽으면 자연어와 공유하는 분포 문제, 편향, 평가 원칙이 분리되기 쉽다고 주장한다.

### D. 이 서베이의 위치와 새로운 점

앞선 세 갈래를 연결해 텍스트와 코드를 공통 틀에서 비교하는 것이 목표다. 공통 분류, 품질과 분포의 비교, 실무적 교훈이라는 기여를 제시한다. 이는 저자가 설정한 문헌상의 위치이며, 기존 서베이보다 모든 주제를 더 자세하게 다룬다는 보편적 우월성 주장으로 확대할 필요는 없다. [저자 공개 원문 §2](https://arxiv.org/pdf/2503.14023v2#page=3)

## III. 서베이 방법론

포함 대상은 주로 2020년 1월부터 2025년 4월까지 발표된 텍스트·코드 관련 연구다. 생성, 증강, 지시 학습을 다루고 경험적 근거나 방법론적 기여가 있어야 한다. 텍스트·코드 밖의 연구는 전이 가능한 통찰을 주는 경우가 아니면 제외하고, 초기 기술은 역사적 기반이 필요한 경우 예외적으로 포함한다.

이 기간은 논문의 출판일과 다르다. 2025년에 출판되었다고 해서 그해 말까지의 흐름을 조사한 것은 아니다. [저자 공개 원문 §3](https://arxiv.org/pdf/2503.14023v2#page=4)

### A. 검토 과정

Google Scholar, arXiv, Semantic Scholar에서 관련 키워드를 검색하고 기존 서베이·평가 논문의 참고문헌을 따라가며 자료를 확장했다. 제목과 초록으로 먼저 제외 대상을 정한 뒤 전체 본문을 포함 기준으로 검토한다. 최종 문헌은 해당 기간의 선별된 표본이라는 설명이므로, 모든 관련 논문의 누락 없는 목록이라고 볼 수는 없다.

### B. 문헌 선별 흐름

Figure 1은 <strong>PRISMA(체계적 문헌고찰 보고 지침)</strong>를 참고한 검색·선별 흐름을 제시한다. 이 그림의 역할은 독자가 자료 선정 경로를 이해하도록 하는 것이다. 생성 알고리즘의 성능 결과를 나타내는 그림은 아니다. [저자 공개 원문 §3 및 Figure 1](https://arxiv.org/pdf/2503.14023v2#page=4)

## IV. 배경과 동기

### A. 합성 데이터

Synthetic Data는 실제 사건이나 사람의 주석을 직접 수집하는 대신 알고리즘이나 생성 모델로 만든 자료다. 역사는 시뮬레이션에서 시작해 단어 치환·삽입·삭제, <strong>Back-Translation(역번역)</strong>, 신경망의 바꿔 쓰기, 모델이 붙인 라벨, LLM 생성으로 이어진다.

Back-Translation은 목표 언어의 실제 문장을 반대 방향으로 번역해 병렬 문장쌍을 만든다. 간단한 단어 변형은 작은 데이터셋의 과적합을 줄일 수 있지만, 새로운 의미와 표현을 풍부하게 만들기에는 한계가 있다. LLM은 과제 설명과 예시만으로도 더 넓은 유형의 데이터를 생성하도록 지시할 수 있다는 점에서 이 계보를 확장한다.

동기는 다섯 가지다. 라벨 수집 비용을 줄이고, 자료를 많이 만들고, 드문 상황이나 특정 속성을 지정하고, 민감한 실제 자료의 직접 사용을 줄이며, 표현의 변화를 늘리는 것이다. 그러나 이 절의 개인정보상 이점은 후반 VII-F의 유출 위험과 함께 읽어야 한다. 생성했다는 사실 자체가 개인정보 보호를 보장하지는 않는다.

Table 2는 비용·시간과 성능이 다른 축이라는 점을 보여준다. 저자판 표에는 사람 라벨 3,000개와 합성 자료 6,000개의 성능이 함께 제시되며, 합성 자료 3,000개의 성능은 미기재다. 따라서 동일 샘플 수의 정확한 성능 비교로 다시 표현하지 않는다. [저자 공개 원문 §4.1 및 Table 2](https://arxiv.org/pdf/2503.14023v2#page=5)

### B. LLM의 프롬프트 기반 데이터 증강

<strong>Zero-Shot Generation(예제 없는 생성)</strong>은 과제 설명만 주며 모델의 사전 지식에 많이 의존한다. 간단하지만 같은 지시를 반복하면 일반적인 표현에 몰릴 수 있다. <strong>One-Shot Generation(예제 하나를 이용한 생성)</strong>은 형식과 문체를 고정하는 데 도움이 되고, <strong>Few-Shot Generation(소수 예제를 이용한 생성)</strong>은 여러 예제로 라벨과 출력 구조를 더 구체적으로 보여준다. 대신 주어진 예제의 패턴을 반복할 수 있다.

주제 제어 방식은 먼저 여러 주제나 상황을 만들고, 각 주제를 조건으로 샘플을 생성한다. 이는 단순히 무작위성을 높이는 대신 전체 생성 범위를 분산시키는 방법이다. 이 절의 핵심은 생성 전략의 선택이 관련성과 다양성 사이의 균형을 바꾼다는 점이다. [저자 공개 원문 §4.2](https://arxiv.org/pdf/2503.14023v2#page=6)

## V. 텍스트 과제의 합성 데이터 생성

### A. 프롬프트 기반 합성 텍스트 생성의 여러 접근

IV-B의 전략을 실제 분류·질의응답·지시 데이터 연구에 연결한다. 저자는 실제 데이터가 적을 때 합성 자료의 도움이 크게 나타나고, 실제 자료가 충분해지면 추가 이득이 줄어드는 연구들을 소개한다. 같은 양의 합성 자료라도 기존 데이터가 채우지 못한 부분이 얼마나 남아 있는지가 중요하다는 해석이다.

방법은 주제와 지시를 바꾸는 방식, 예제로 형식·라벨을 맞추는 방식, 반복 생성과 피드백으로 자료를 보완하는 방식으로 정리된다. 실제 자료를 섞으면 현실의 분포를 잡아주는 역할을 하므로, 합성 자료만 사용할 때와 다른 생성 전략이 적절할 수 있다.

Table 3에는 GPT3Mix, Unnatural Instructions, Self-Instruct 등 여러 연구가 배치된다. 다만 서베이 표의 개별 데이터셋 설명은 해당 연구의 원문을 대신하지 않는다. 이 해설은 표의 모든 시스템·수치 설명을 재전달하기보다, 이 절의 핵심인 프롬프트 선택과 실제 데이터량의 관계를 정리한다. [저자 공개 원문 §5.1](https://arxiv.org/pdf/2503.14023v2#page=7)

### B. 생성 데이터의 품질과 속성

생성 전에 외부 근거를 넣거나, 생성 후에 품질이 낮은 결과를 제거하는 두 접근을 비교한다. <strong>Retrieval-Augmented Generation(검색 증강 생성, RAG)</strong>은 관련 문서를 제공해 그 안에서 질문과 답을 만들게 한다. 원문은 이를 근거 연결의 장점으로 제시한다. 다만 같은 절 후반이 추론 오류를 별도로 다루므로, 문서를 제공했다는 이유만으로 모든 답과 설명이 검증되었다고 읽지 않는다.

후처리에서는 중복, 예제의 그대로 복사, 형식 위반을 제거한다. 더 복잡한 방식은 평가 모델, 높은 라벨 신뢰도, 여러 응답 사이의 일관성을 활용한다. 사람에게 일부를 검토하게 하고 그 결과로 자동 필터를 조정하는 방식도 있다. 핵심은 대량 생성과 품질 판단을 별도 과정으로 만든다는 것이다. [저자 공개 원문 §5.2](https://arxiv.org/pdf/2503.14023v2#page=9)

#### 1) 분포 정렬

<strong>Distribution Alignment(분포 정렬)</strong>은 내용이 맞는지와 다른 문제다. 실제 사용자가 짧고 거칠게 쓰는 영역에서 모델이 지나치게 정제된 문장만 만들면, 올바른 샘플도 평가 환경을 잘 대표하지 못한다. 실제 오분류 사례를 겨냥하거나 현실의 주제 범위를 맞추는 방법이 소개된다. 따라서 품질에는 샘플의 정답성뿐 아니라 데이터셋이 어디에 쓰일지에 대한 적합성이 포함된다.

#### 2) 합성 질의응답과 추론

<strong>Question Answering(질의응답, QA)</strong>에서 최종 답뿐 아니라 <strong>Chain-of-Thought(사고 연쇄, CoT)</strong>를 생성하면 답변 내용과 추론 형식을 함께 학습시킬 수 있다. 문제는 답이 맞더라도 중간 설명이 틀릴 수 있다는 점이다. 최종 답 확인과 계산기·지식 기반을 통한 중간 사실 확인이 서로 다른 역할을 한다. 이 절은 설명이 길거나 자연스럽다는 사실과 추론이 타당하다는 사실을 구별하게 한다. [저자 공개 원문 §5.2 후반](https://arxiv.org/pdf/2503.14023v2#page=9)

### C. 마무리

텍스트 생성에서는 수량·다양성·정확성·관련성의 균형이 필요하다고 정리한다. 검색, 오류 피드백, 필터링이 이 균형을 돕는다. 일부 과제에서 실제 데이터에 가까운 효용이 나타났다는 결과를 모든 도메인에서 실제 데이터를 대체할 수 있다는 주장으로 확대하지 않는다. 다음 절은 더 명확한 실행 신호가 있는 코드에서 같은 원리가 어떻게 바뀌는지 살펴본다. [저자 공개 원문 §5.3](https://arxiv.org/pdf/2503.14023v2#page=9)

## VI. 코드 과제의 합성 데이터 생성

### A. 프롬프트 기반 합성 코드 생성의 여러 접근

코드 완성, 번역, 수정, 질의응답을 위한 데이터를 구분한다. 기존 저장소의 코드로 사전학습하는 것과 특정 기능을 학습시키기 위해 합성 예제를 만드는 것은 역할이 다르다. 이 절은 합성 자료의 형태를 지시–해답, 언어 간 대응 코드, 문제–해결책, 오류–수정으로 확장한다. [저자 공개 원문 §6.1](https://arxiv.org/pdf/2503.14023v2#page=10)

#### 1) 지시 따르기 접근

Code Alpaca는 시드 지시에서 새로운 프로그래밍 지시와 해답을 만드는 사례다. WizardCoder는 지시의 복잡성을 반복적으로 높이며, Magicoder는 오픈소스 코드와 연결된 지시 데이터를 만드는 접근으로 소개된다.

공통점은 원시 코드의 양을 늘리는 것보다, 사용자의 요청을 코드 해답에 연결하는 <strong>Instruction Tuning(지시 미세조정)</strong> 자료를 만든다는 데 있다. 서베이가 요약한 개별 시스템의 구현 설명 전체를 재현한 것은 아니며, 세 방법의 공통 역할을 중심으로 읽는다.

#### 2) 코드 번역과 리팩터링

<strong>Code Translation(코드 번역)</strong>은 여러 프로그래밍 언어 사이의 대응 데이터를 만든다. <strong>Refactoring(리팩터링)</strong>은 기능을 유지하면서 변수명, 형식, 주석, 구조를 바꿔 같은 기능의 여러 표현을 제공한다. 이 차이를 통해 모델이 특정 토큰 패턴에만 의존하지 않도록 할 수 있다.

LintSeq는 완성 코드만 제공하는 대신 점진적 수정의 연속을 만드는 사례로 소개된다. 결과뿐 아니라 변환 과정도 학습 자료의 단위가 될 수 있다는 점에서 앞의 지시–해답 쌍을 확장한다. 기능을 유지한다는 목적과 실제로 유지되었는지를 검증하는 작업은 다음 품질 절로 이어진다.

#### 3) 문제 생성과 해답 합성

문제 설명과 정답 코드를 함께 만들거나, 정상 코드에 오류를 넣고 수정본과 짝지을 수 있다. 논문은 학생이 흔히 내는 오류를 모사하는 LLM-itation과, 실행 후 고치는 과정을 자료로 만드는 접근을 소개한다. 올바른 해답만이 아니라 실패와 복구도 유용한 학습 신호라는 주장이다.

이 절의 일부 시스템 귀속·구현 설명은 서베이만으로 확정하기 어렵다. 따라서 AlphaCode의 개발 주체·기반 모델 등 부수적 설명은 이 해설에서 재전달하지 않는다. 이 절에서 확인할 수 있는 중심 논지는 후보 생성, 실행 확인, 오류 사례의 데이터화라는 방법적 구분이다. [저자 공개 원문 §6.1.1–6.1.3](https://arxiv.org/pdf/2503.14023v2#page=10)

### B. 생성 데이터의 품질과 속성

#### 1) 실행 피드백과 검증

Execution Feedback은 네 용도로 구분된다.

- **해답 선별:** 생성한 후보를 테스트하고 통과한 것을 남긴다.
- **실패로부터 학습:** 오류 메시지와 재시도를 연결해 수정 과정을 만든다.
- **보상 신호:** <strong>Reinforcement Learning(강화학습, RL)</strong>에서 실행 결과를 보상으로 사용한다.
- **난이도 추정:** 성공까지 필요한 시도나 실패 패턴을 자료의 난이도 구분에 활용한다.

정적인 정답 코드 모음을 학습하는 방식과, 학습 도중 새로운 코드를 생성하고 보상을 받는 방식은 구별된다. 저자는 자연어의 사실 판단보다 실행의 통과·실패가 명확하다는 점을 강조한다. 그 주장은 설정한 테스트에서 얻은 신호에 관한 것이며, 이 절에 모든 입력에 대한 프로그램의 완전한 정확성을 증명하는 방법은 없다. [저자 공개 원문 §6.2](https://arxiv.org/pdf/2503.14023v2#page=12)

#### 2) 코드의 편향과 데이터 범위

코드에서도 특정 라이브러리, 반복문 형태, 변수명, 최신·구형 문법에 편중될 수 있다. 같은 기능을 여러 방식으로 구현하고, 주석과 이름을 바꾸며, 드문 언어 기능과 경계 상황을 포함하는 접근이 소개된다.

이는 정확한 프로그램을 많이 모으는 것만으로 부족하다는 뜻이다. 익숙한 과제와 구현 방식만 반복하면 코드의 긴 꼬리 영역은 여전히 비어 있을 수 있다. 이 절은 텍스트에서의 주제·문체 다양성에 대응하는 코드의 기능·구조·언어 범위를 다룬다. [저자 공개 원문 §6.2 후반](https://arxiv.org/pdf/2503.14023v2#page=13)

### C. 마무리

저자는 실제 코드 중심 사전학습과 합성 지시 데이터 중심 후속 학습이 결합되는 흐름을 정리한다. 자연어–SQL처럼 특화된 과제에서도 다양한 질문과 검증된 코드 쌍이 유용할 수 있다고 설명한다.

다만 원문은 Qwen 관련 예시의 이름에 가정적 표현을 직접 붙인다. 이 문장을 실제 모델의 검증된 학습 절차나 비교 실험으로 인용하지 않는다. 이 절의 일반적 결론은 코드의 검증 가능성이 합성 자료 활용을 돕는다는 것이지, 특정 모델에 대한 모든 서술이 독립적으로 입증되었다는 것이 아니다. [저자 공개 원문 §6.3](https://arxiv.org/pdf/2503.14023v2#page=13)

## VII. 문제점과 고려 사항

### A. 품질 보증과 사실성

텍스트의 잘못된 사실과 코드의 잘못된 기능이 그대로 다음 모델의 학습 신호가 될 수 있다. 검색, 실행, 평가 모델, 정적 분석, 사람의 표본 검토가 완화 방법이다. 원문은 언어 모델의 <strong>Perplexity(퍼플렉시티)</strong>를 품질의 대리 신호로 쓰는 아이디어도 언급한다. 이는 모델에게 얼마나 예상 가능한 문장인지를 보는 신호이며, 이 절에서 사실 정확성을 보장하는 지표로 입증된 것은 아니다. [저자 공개 원문 §7.1](https://arxiv.org/pdf/2503.14023v2#page=14)

### B. 분포 변화와 현실성

<strong>Distribution Shift(분포 변화)</strong>는 학습용 생성 데이터와 실제 사용 데이터가 다른 현상이다. 정제된 텍스트와 실제의 오타·속어, 특정 코딩 방식과 다양한 실제 코딩 방식 사이의 차이를 예로 든다.

실제 자료와의 혼합, 여러 모델·프롬프트 사용, 분포를 구별하는 판별기, 생성 비율의 점진적 변경 등이 제안된다. 편향을 가진 생성기가 반복적으로 자료를 만들면 그 편향도 이어질 수 있으므로, 생성 조건과 사후 구성 조절을 함께 다룬다. 제안된 모든 대책이 동일한 실험으로 비교된 것은 아니다. [저자 공개 원문 §7.2](https://arxiv.org/pdf/2503.14023v2#page=14)

### C. 합성 데이터와 학습 모델의 평가

원문은 데이터 자체의 속성과, 그 자료로 학습한 모델의 실제 과제 성능을 함께 평가하라고 제안한다. 실제 데이터만, 합성 데이터만, 혼합한 경우를 비교하고 독립된 실제 평가 자료에서 성능을 살핀다. 다양성·현실성, 사람의 판단, 드문 사례에 대한 일반화도 별도 축이다.

코드의 <strong>pass@k(k개 후보 중 정답을 포함하는 성과 지표)</strong>, 실행 정확도, 문법·논리 오류 분류는 서로 다른 정보를 준다. 텍스트의 자동 지표도 다양성과 성능을 각각 다른 방식으로 측정하므로, 하나의 점수가 모든 품질을 대표하지 않는다. [저자 공개 원문 §7.3](https://arxiv.org/pdf/2503.14023v2#page=15)

#### 1) 통계적 엄밀성과 견고성

저자는 반복 실험, <strong>Confidence Interval(신뢰구간)</strong>, 다른 데이터셋에서의 검증, 통계 검정을 권고한다. 목적은 관측된 개선이 특정 분할이나 우연에 의존하는지 구별하는 것이다. 실제 자료 기준선, 합성 자료 구성, 오류와 분포 차이를 함께 공개할 것도 요구한다. 이는 앞으로의 평가에 대한 권고이며, 서베이에 등장한 모든 연구가 이미 이런 절차를 수행했다는 의미는 아니다. [저자 공개 원문 §7.3 후반](https://arxiv.org/pdf/2503.14023v2#page=15)

### D. 폐쇄형 반복 생성의 과적합과 분포 변화

<strong>Model Collapse(모델 붕괴)</strong>는 앞선 모델의 출력으로 다음 모델을 반복 학습할 때 오류·편향·패턴이 누적되어 일반화가 약해지는 문제로 다룬다. 합성 자료를 한 번 추가하는 상황과, 여러 세대에 걸쳐 실제 자료를 대체하는 상황을 구별해야 한다.

실제 자료를 유지하고, 합성 자료를 검증하며, 분포 변화와 과적합을 관찰하는 방법이 제시된다. 실제 자료의 유지가 위험을 줄인다는 인용 결과를 어떤 비율·모델·과제에서도 붕괴하지 않는다는 보장으로 해석할 수는 없다. [저자 공개 원문 §7.4](https://arxiv.org/pdf/2503.14023v2#page=15)

### E. 규모와 비용의 절충

생성은 사람의 직접 작성보다 저렴할 수 있지만 호출·시간·검증 비용이 들며, 더 많은 자료가 항상 더 많은 이득을 주지 않는다. 강한 모델로 적게 만들지, 저렴한 모델로 많이 만든 후 걸러낼지, 생성기와 평가기를 분리할지가 설계 변수다.

재현성도 문제다. 같은 서비스에 같은 요청을 해도 생성 자료가 달라질 수 있으므로 DataDreamer 같은 표준화 도구가 소개된다. 이 절은 비용을 단순한 생성 단가가 아니라 재현 가능한 전체 과정의 비용으로 보게 한다. [저자 공개 원문 §7.5](https://arxiv.org/pdf/2503.14023v2#page=16)

### F. 윤리와 법적 고려

Synthetic Data라도 모델이 기억한 개인정보·저작물·편향이 나타날 수 있다. 따라서 ‘인공적으로 만들었다’와 ‘안전하게 공유할 수 있다’를 동일시하지 않는다. 이 절은 유사한 원문 재생성과 민감 정보의 노출을 확인할 필요성을 설명하며, 구체적 관할의 법률 판단을 제공하는 절은 아니다.

후반은 Model Collapse로 돌아가 실제 자료를 버리는 대체 방식과 실제·합성 자료를 함께 축적하는 방식을 비교한다. 위험을 결정하는 것은 합성 여부 하나가 아니라 반복 과정에서 어떤 정보가 보존되는가라는 점이다. [저자 공개 원문 §7.6](https://arxiv.org/pdf/2503.14023v2#page=16)

### G. 과제별 차이

대화에서는 LLM이 양쪽 화자를 맡으면 실제 사용자보다 지나치게 협조적일 수 있다. 요약에서는 표현만 비슷하게 여러 개 만드는 것보다 서로 다른 초점을 반영하는 것이 중요하다. 드문 프로그래밍 언어에서는 생성기의 지식 자체가 부족하므로 알려진 언어에서 번역하는 등의 다른 접근이 필요할 수 있다.

앞의 공통 원칙을 적용하더라도 실패 형태는 과제마다 다르다는 점을 정리한다. 하나의 범용 품질 필터만으로 모든 응용을 처리할 수 있다는 주장은 하지 않는다. [저자 공개 원문 §7.7](https://arxiv.org/pdf/2503.14023v2#page=17)

### H. 사람의 수용

실제 현장에서 쓰려면 생성 방법과 평가 결과를 설명할 수 있어야 한다. 사람의 수용은 ‘AI가 만들었으니 믿는다’는 태도가 아니라, 실제 자료에서 작동한다는 근거와 투명성에 연결된다. 이 절은 성능 측정에서 현장 도입으로 논의를 옮기며, 다음 절의 평가·전문가 협업 방향을 준비한다. [저자 공개 원문 §7.8](https://arxiv.org/pdf/2503.14023v2#page=17)

## VIII. 미래 방향

원문은 아래 항목을 별도 번호 없는 연구 방향 목록으로 제시한다. 이미 검증된 통합 시스템의 기능 목록이 아니라, 앞 절에서 드러난 문제에 대한 제안이다.

- **통합 틀과 분류:** 생성부터 필터링·학습까지 같은 언어로 기술해 방법을 비교하도록 한다.
- **프롬프트 자동화:** 사람이 문구를 반복 조절하는 대신 생성 자료의 학습 효용에 맞춰 지시를 최적화한다.
- **능동학습과 생성기의 결합:** 학습 모델이 불확실한 영역을 식별하고 그 영역의 예제를 요청한다.
- **다중양식 확장:** 이미지·음성·영상과 텍스트를 짝짓는 데이터로 확장하되, 두 표현이 실제로 맞물리는지 검증해야 한다.
- **실제 자료의 조건부 변형:** 완전히 새로 생성하기보다 바꿀 속성과 유지할 속성을 정해 대응 예제를 만든다.
- **이론적 이해:** 생성 분포와 학습 알고리즘이 일반화에 어떤 영향을 주며, 언제 추가 생성의 이득이 줄어드는지 설명한다.
- **품질 평가 지표:** 전체 모델을 매번 학습하지 않고도 실제 학습 효용을 예측하는 지표를 찾는다.
- **전문가와의 상호작용:** 도메인 제약과 사람의 수정을 다음 생성에 반영한다.
- **안전 필터와 편향 완화:** 유해한 내용과 구성의 편중을 생성·검증 과정에서 조절한다.
- **분야별 생성기:** 의료·법률·다국어 등에서 범용 모델보다 해당 분야 자료 생성에 맞춘 모델을 탐색한다.
- **평가 대회와 공통 과제:** 제한된 실제 자료에서 생성한 데이터가 숨겨진 실제 평가셋의 성능을 얼마나 높이는지 비교한다.

공통 방향은 생성기의 출력 자체가 아니라, 최종 학습 효용과 도메인 제약을 기준으로 전체 과정을 조정하는 것이다. Table 6은 이 의제를 평가·윤리·프롬프트·다중양식·사람 참여·분야별 생성·평가 체계로 압축한다. [저자 공개 원문 §8](https://arxiv.org/pdf/2503.14023v2#page=17)

## IX. 결론

텍스트에서는 자료가 적은 상황의 보완, 코드에서는 실행 확인을 이용한 자료 구축이 두드러진다고 정리한다. 두 영역 모두 생성 조건, 필터링, 실제 자료와의 혼합이 중요하며, 오류와 분포 변화는 계속 남는 문제다.

이 서베이는 전통적 증강에서 LLM 기반 생성으로 이어지는 배경과 텍스트·코드의 비교를 얻는 데 유용하다. 개별 시스템의 수치나 구현을 실험 근거로 사용할 때는 해당 1차 논문을 다시 확인해야 한다. 특히 본문에 가정적 사례가 포함되어 있다는 점을 고려해, 전망과 실제 보고 결과를 나누어 읽는다. [저자 공개 원문 §9](https://arxiv.org/pdf/2503.14023v2#page=19)
