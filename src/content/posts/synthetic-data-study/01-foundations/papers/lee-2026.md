[논문 원문 열기](https://arxiv.org/html/2607.16900)

## 초록

Large Language Model(대규모 언어 모델, LLM)을 사용하는 API-calling Agent(API 호출 에이전트)는 명령 한 번의 정답뿐 아니라 여러 호출과 응답이 이어지는 Trajectory(행동 궤적)로 학습해야 한다. 저자들은 실제 API 서버와 데이터베이스를 만드는 비용을 줄이기 위해 ESAT이라는 생성 절차를 제안한다. API Specification(API 명세)에서 과제를 만들고, LLM이 환경 응답을 모사하며, 다른 평가 단계가 Trajectory를 선별한다. 핵심 근거는 모사 데이터로 학습한 모델을 실제 AppWorld와 OfficeBench에서 평가한 결과다. [원문](https://arxiv.org/html/2607.16900)

## 1 서론

일반적인 지시문 데이터와 달리 Agent 학습에는 조회·변경·오류 복구·상태 추적이 연결된 자료가 필요하다. 기존 생성 방식이 실행 가능한 환경과 그 안을 채울 상태 데이터에 의존한다는 점을 병목으로 규정한다.

ESAT은 **과제 생성 → Agent와 Simulator(모사기)의 상호작용 → 완성된 Trajectory 선별**로 이를 분리한다. 여기서 “환경 없이”란 학습 데이터 생성에 실제 API 실행 결과를 요구하지 않는다는 뜻이다. 이후 실험의 평가 환경까지 없앤다는 뜻은 아니다. LLM이 호출 이력을 조건으로 다음 응답을 만들 수 있다는 가설을 실제 환경 전이로 검증하는 것이 논문의 구조다. [§1](https://arxiv.org/html/2607.16900#S1)

왼쪽 API 명세가 과제 생성과 검사를 거쳐 가운데 Agent–Simulator 반복 호출로 연결되고, 오른쪽 Judge가 완성된 Trajectory를 고른다. 실제 응답을 수집하는 대신 Simulator가 반환값을 만든다는 점이 핵심이다. 도식의 단계 구분은 각 단계의 판정이 독립적인 실제 환경 검증을 보장한다는 뜻은 아니다.

## 2 관련 연구

### 실행 가능한 환경을 사용하는 합성 데이터

기존 연구는 호출을 실제 서비스나 구현된 샌드박스에서 실행해 응답을 얻는다. 관측이 실제 상태에 연결된다는 장점이 있지만, 새 API를 다룰 때마다 환경 구축과 상태 데이터 수집이 필요하다. 이 절은 ESAT이 줄이려는 비용이 무엇인지 구체화한다.

### API Simulator로서의 LLM

ToolAlpaca, ToolACE, ToolEmu, StableToolBench, Simia 등과 비교한다. 저자들이 강조하는 차이는 변경 API 지원, 명세에서 과제까지 생성하는 구성, Agent와 Simulator의 단계별 분리, 호출 이력을 통한 상태 유지다. 이는 모든 기존 연구가 단일 호출만 다룬다는 주장이 아니라, 긴 상태 기반 작업을 지원하는 설계의 차이에 관한 주장이다. [§2](https://arxiv.org/html/2607.16900#S2)

## 3 방법

외부 입력은 API 이름·설명·입출력 Schema(구조 명세)다. 생성 과정 자체에 사람의 개별 과제 작성이나 실제 사용자 데이터베이스를 요구하지 않도록 세 단계를 구성한다. [§3](https://arxiv.org/html/2607.16900#S3)

### 3.1 과제 생성

#### 구간별 생성

난이도, 조회·변경 비중, 추론 유형, 앱 수, 앱별 API 수를 조합한 Bucket(생성 구간)을 사용한다. 같은 생성 요청을 반복하는 대신 목표 분포를 먼저 나누는 방식이다.

#### 역빈도 기반 표집

이미 자주 사용한 앱에는 낮은 선택 확률을 주고, 적게 사용한 API를 생성 요청에서 강조한다. 생성량이 늘면서 특정 기능만 반복되는 문제를 완화하려는 장치다.

#### 과제 선별

LLM Judge(모델 평가자)가 제공된 API만으로 해결 가능한지, 표현이 명확한지, Bucket 요구를 지키는지 판정한다. 실행 가능한 정답 검증과 같은 보장은 아니며, 과제 수준의 모델 판정이다.

#### 과제 재작성

절차를 지나치게 설명하는 문장을 사용자 목표 중심 요청으로 줄인다. 재작성 뒤 다시 검토하며, 본문은 거절된 재작성 대신 원래 과제를 사용한다고 설명한다. 다만 부록 G.5에는 최종 거절 과제를 제외한다고 쓰여 있어 처리 규칙의 서술이 일치하지 않는다. 이 차이를 임의로 하나의 구현으로 확정할 수는 없다. [§3.1](https://arxiv.org/html/2607.16900#S3.SS1)

### 3.2 Trajectory 생성

Teacher Model(교사 모델)이 API를 호출하면 Simulator는 명세, 입력 인자, 과제, 이전 호출과 응답, 가상 사용자, 고정된 날짜·시간을 받아 응답한다. 이력은 **동일 과제 안의 동일 앱**으로 제한한다. 모든 앱의 전역 상태를 하나의 데이터베이스처럼 검사하는 구조로 읽으면 안 된다.

#### Simulator 규칙

이전에 만든 항목의 속성과 변경을 유지하고, 과제와 무관한 항목도 섞으며, 현실적인 값과 Schema를 지키도록 지시한다. 관련 항목만 반환하는 지나치게 쉬운 환경을 피하려는 설계다.

#### 모사 품질 검사

입력 인자는 프로그램으로 검사한다. 응답은 파싱·Schema 검사와 의미 검사를 거쳐, 실패 이유를 피드백으로 받아 재생성한다. **부록 H.5의 상세 구현에서는 의미 검사를 GET에만 적용하고, 변경 호출은 구조 검사 통과 시 수용한다.** 본문의 포괄적인 설명과 이 구현 범위를 함께 읽어야 한다.

#### Trajectory 종료

완료 API 호출, 단계 한도 초과, 허용된 앱 밖의 API 호출, Simulator 실패가 종료 조건이다. 완료 신호를 보냈다는 사실과 과제를 올바르게 해결했다는 사실은 구분하고, 후자는 다음 단계에서 판단한다. [§3.2](https://arxiv.org/html/2607.16900#S3.SS2)

### 3.3 Trajectory 선별

완료 신호까지 도달한 Trajectory를 여러 번 평가해 다수의 긍정 판정을 받은 것만 남긴다. 생성기 내부의 응답 검사와 전체 해결 과정의 검사는 다른 역할이다. 후자는 요청 충족, 정보 연결, 중복과 불필요한 행동까지 살핀다. [§3.3](https://arxiv.org/html/2607.16900#S3.SS3)

## 4 실험

### 평가 환경

AppWorld에서는 일반 평가와 더 어려운 평가를 구분하며, 어려운 평가의 두 앱을 생성에서 제외한다. OfficeBench는 원래 환경 전체가 아니라 OCR 의존·해결 불가능 과제를 제외한 2개 앱 과제 26개와 3개 앱 과제 46개를 평가한다.

### 모델

과제 생성에는 GLM-4.7-FP8, Teacher와 Simulator에는 GLM-5.1-FP8, 최종 선별에는 Gemini-3.1-Pro를 사용한다. 학생은 Qwen3와 Qwen3.5 계열이다.

### 학습

Supervised Fine-Tuning(지도 미세조정, SFT)으로 이전 과제·호출·응답을 조건으로 현재 Agent 출력을 예측한다. Simulator 응답 자체를 정답 행동으로 학습하는 구성은 아니다.

### 평가

여덟 번의 추론 실행을 평균하고 부록 F에 표준편차를 제시한다. 여러 후보 중 하나라도 성공하면 성공으로 세는 값과 혼동하지 않도록, 부록 D는 평균 pass@1이라고 명시한다. [§4](https://arxiv.org/html/2607.16900#S4)

### 4.1 AppWorld 결과

#### AppWorld API로 만든 ESAT 데이터

ESAT-AW7은 학습에 허용한 일곱 앱의 명세를 사용한다. 평가 과제를 학습 예제로 직접 가져오는 대신 API 정보만 활용하는 조건이다.

#### 합성 API로 만든 ESAT 데이터

ESAT-S52는 별도 합성 앱의 명세로 생성한다. 다만 부록 K의 앱 설계에는 AppWorld의 API를 구조 예시로 사용한다. 따라서 “독립”은 같은 앱·사용자 상태를 그대로 사용하는 것이 아니라 별도 앱을 구성한다는 의미로 읽어야 한다.

#### AppWorld 학습 데이터

AWT는 공식 학습 과제 90개에서 실제 환경을 실행한 뒤 검증기를 통과한 634개 Trajectory다. ESAT과 AWT 비교는 데이터 크기까지 동일하게 통제한 비교는 아니다.

#### 지표

Task Goal Completion(과제 목표 완료, TGC)을 본문에, Scenario Goal Completion(시나리오 목표 완료, SGC)을 부록에 보고한다.

Test-N과 Test-C는 서로 다른 평가 분할이며 값은 여덟 추론 실행의 평균 백분율이다. 괄호는 행에 따라 zero-shot 또는 AWT 기준의 차이다. Qwen3.5의 추가 AWT 행은 개선이 없어 이전 ESAT 결과를 반복 기재했다. 전체 표를 재현했다.

##### 새로운 API로의 일반화

ESAT-S52 학습은 AppWorld 앱으로 만들지 않은 데이터에서도 성능 개선을 보인다. 이는 API를 읽고 결과를 연결하는 능력의 전이를 지지한다.

##### 최소한의 목표 도메인 정보로 얻은 개선

ESAT-S52와 ESAT-AW7의 결합이 대체로 추가 이득을 준다. 예를 들어 Qwen3-8B의 AppWorld TGC는 ESAT-S52의 Test-N 59.3, Test-C 45.6에서 결합 데이터의 64.9, 49.1로 높아졌다. AWT만 학습한 조건은 각각 55.7, 39.1이다. 모든 수치는 표 1의 여덟 실행 평균 백분율이다.

##### 효과적인 지식 전달

일부 작은 학생 모델이 비교 대상 대형 모델보다 높은 성능을 보인다. 이는 해당 데이터·평가 조건에서의 Knowledge Distillation(지식 증류) 결과이며, 모든 작업에서 작은 모델이 우월하다는 결론은 아니다.

##### 새로운 사용자 데이터 패턴으로의 일반화

Simulator가 만든 가상 상태로 학습했는데 실제 평가 상태에서도 이득이 나타난다. 저자들은 이를 상태 패턴의 전이 근거로 해석한다. 가능한 모든 상태 변화에 대한 일관성을 증명한 것은 아니다. [§4.1](https://arxiv.org/html/2607.16900#S4.SS1)

#### 실제 환경의 정답 판정과의 관계

수용 100개·거절 100개로 구성한 200개 표본에서 사람과의 일치율은 95%, Cohen’s kappa(우연 일치를 보정한 일치도)는 0.90이었다. 균형 표본으로 구성한 사람 평가와 실제 환경 검증은 서로 다른 근거다. [§4.3](https://arxiv.org/html/2607.16900#S4.SS3)

#### 응답 길이의 효과

짧은 응답보다 긴 응답에서 검사 실패가 늘었다. 저자들은 사용하는 Simulator의 장문 일관성 한계가 원인일 가능성을 제시하며, 입력 문맥 길이에서는 뚜렷한 관계를 관찰하지 못했다고 보고한다. 강한 모델로 해결할 수 있다는 내용은 향후 가능성이지 이 논문이 실행해 입증한 결과는 아니다. [§4.4](https://arxiv.org/html/2607.16900#S4.SS4)

### 4.5 기존 합성 API 호출 데이터와의 비교

ToolAlpaca, ToolACE, Nemotron 데이터로 학습한 모델과 비교한다. ESAT은 두 평가 환경에서 더 큰 개선을 보이며, 다른 합성 데이터 뒤 AWT로 추가 학습해도 차이가 남는다. 저자들은 긴 조회·변경 연쇄와 상태 추적이 대상 작업에 맞기 때문이라고 해석한다. 이는 전체 파이프라인 비교이며, 상태 유지 하나의 효과만 분리한 실험은 아니다. [§4.5](https://arxiv.org/html/2607.16900#S4.SS5)

## 5 결론

API 명세, Coverage(범위 포괄) 중심 과제 생성, 상태를 조건으로 한 모사, 전체 Trajectory 선별을 결합하면 실행 환경 없이도 유용한 학습 자료를 얻을 수 있다는 주장으로 마무리한다. 근거 범위는 AppWorld와 OfficeBench에서의 SFT 효과다. [§5](https://arxiv.org/html/2607.16900#S5)

## 부록 A ESAT-AW7 데이터 통계

### A.1 생성 처리량과 수율

#### 과제 생성 처리량

초기 과제, 첫 평가 통과, 재작성, 최종 평가의 단계별 수를 제공한다. 첫 판정을 통과한 과제 수와 재작성 최종 통과 수가 다르므로 단순한 일렬 필터로만 읽을 수 없으며, 원래 과제로 복귀하는 본문 설명을 함께 확인해야 한다.

#### Trajectory 생성 처리량

입력 과제 14,361개에서 완료 11,445개, 최종 수용 9,352개가 남는다. 완료와 정답 수용을 분리해 비용과 수율을 보여준다.

### A.2 실패 분석

#### Trajectory 생성 실패 유형

Simulator 실패와 Judge 거절이 주요 원인이다. 시간 초과·형식/의미 검사 한도 소진과, 끝까지 수행했지만 답이 틀린 사례를 구분한다.

#### 과제 분포

난이도·행동·과제 유형은 비교적 넓게 분포하지만, 여러 앱을 잇는 과제는 적다.

## 부록 D 구현 세부 사항

### 데이터 합성

Teacher 단계 한도는 AppWorld 50, OfficeBench 30이다. 완료하지 못한 Trajectory는 중단한다.

### 학습

현재 Agent 출력에만 학습 손실을 적용하고 이전 문맥은 가린다. AdamW, 학습률 0.00002, 문맥 길이 32,768을 사용한다. 기본 10 epoch(데이터 반복 학습)이지만 Qwen3.5는 과적합 관찰로 5 epoch를 사용한다. 합성 데이터 학습 단계의 모델 선택에는 AppWorld train과 dev가 쓰인다. 따라서 “명세만 사용”은 생성 입력에 대한 주장이지 모델 선택까지 목표 환경과 완전히 분리했다는 뜻은 아니다.

### 추론과 평가

추론 온도는 1.0이고 과제당 여덟 독립 실행의 평균 pass@1을 보고한다. OfficeBench에는 별도 dev가 없어 AppWorld의 설정을 사용한다. [부록 D](https://arxiv.org/html/2607.16900#A4)

## 부록 G 과제 생성

### G.1 구간별 생성

난이도 3종, 행동 3종, 과제 유형 4종, 앱 수에 따른 API 수 범위를 조합해 360개 Bucket을 구성한다. 어려운 조합에는 더 긴 생성 예산을 준다.

### G.2 역빈도 기반 표집

앱 선택 확률은 $p(a) \propto \frac{1}{1+c(a)}$다. $c(a)$는 현재까지 사용 횟수다. 1을 더해 한 번도 사용하지 않은 앱도 유한한 확률로 선택하며, 많이 등장한 앱의 비중을 낮춘다. API는 사용이 적은 상위 열 개를 강조하되 전체 명세를 함께 제공한다.

### G.3 과제 판정

평가자는 생성기와 같은 요구사항을 받고, 실제 해결 절차를 짧게 검토한 뒤 통과 여부를 결정한다.

### G.4 과제 재작성

목표와 필수 조건은 유지하면서 당연한 중간 절차를 덜어낸다. 원문의 전후 예시는 문장 길이를 줄이는 것보다 사용자 의도와 API 범위를 보존하는 일이 기준임을 보여준다.

### G.5 최종 재판정

재작성에서 조건이 사라지거나 범위가 바뀌는지 확인한다. 이 절은 거절된 과제를 제외한다고 쓰지만 본문 §3.1과 통계 부록은 원래 과제로 복귀한다고 설명한다. 코드 확인 없이 이 불일치를 해소해 서술하지 않는다.

### G.6 과제 생성용 프롬프트

#### 과제 생성 프롬프트

해결 가능성, 명확성, 서로 의존하는 하위 작업, 목표 중심 표현, API Coverage를 요구한다. API를 새로 지어내지 않도록 문서 범위를 명시한다.

#### 과제 Judge 프롬프트

같은 요구를 기준으로 판단 이유와 최종 판정을 분리해 출력한다.

#### 과제 재작성 프롬프트

파일명·경로·날짜·금액·사용자 조건은 유지한다. 원문이 공개한 전후 예시가 스타일 제어를 위한 시범 역할을 한다. [부록 G](https://arxiv.org/html/2607.16900#A7)

## 부록 H Simulator 상세

### H.1 과제·앱별 이력

승인한 호출과 응답을 앱별로 기록하고 과제 종료 시 지운다. 이력 길이에는 한도가 있으며, 실제 사용에서는 그보다 짧았다고 설명한다.

### H.2 결정적 입력 검증

알 수 없는 인자, 필수 값 누락, 타입 불일치, 범위·길이·열거형 위반 등을 프로그램으로 검사한다. 같은 잘못된 호출에 같은 오류를 주어 학습 신호를 안정화한다.

### H.3 프롬프트 구성

명세·인자·응답 Schema·과제·이력·가상 사용자·시간을 매 호출에 제공한다. 상태는 이 텍스트 문맥을 통해 표현된다.

### H.4 출력 Schema 검증

원시 응답의 코드 울타리를 제거한 뒤 파싱한다. 정상 Schema 또는 `{"message": "오류 설명"}` 형태의 실패 Schema 중 하나를 만족하면 구조 검사를 통과한다. 실제 실패 응답도 허용된 결과다.

### H.5 Simulator Judge

GET은 의미·이력 일관성을 추가 판정한다. POST·PATCH·DELETE는 구조 검사를 통과하면 수용한다. 저자들은 변경 응답이 단순 확인 문구인 경우가 많고 비용을 줄일 수 있다는 이유를 든다. 따라서 변경 상태의 정확성이 모든 호출에서 독립적으로 검증된다는 주장은 피해야 한다.

### H.6 구조화된 피드백을 사용한 재시도

형식 오류와 의미 오류에 별도 예산을 둔다. 거절 응답과 구체적인 오류를 대화에 추가하고 다시 생성한다. 어느 예산이든 소진하면 전체 Trajectory를 중단한다.

### H.7 Simulator 프롬프트

#### 모사 규칙

사용자 정보, 응답 Schema, 목록과 페이지, 데이터 일관성, 현실적 값, 관련·비관련 항목 혼합을 규정한다. 페이지 규칙 등은 이 Simulator의 생성 정책이며 실제 모든 API의 동작을 대표하지 않는다.

#### Simulator 시스템 프롬프트

역할과 공통 규칙을 고정해 호출마다 같은 평가 기준을 적용한다.

#### Simulator 사용자 프롬프트 틀

현재 호출과 상태 문맥을 넣고 원시 JSON만 출력하도록 한다.

#### Simulator Judge 시스템 프롬프트

동일한 규칙을 평가자에게 제공하고 페이지 때문에 일부 항목만 반환될 수 있다는 점을 고려하게 한다.

#### Simulator Judge 사용자 프롬프트 틀

후보 응답과 문맥을 함께 보여주고 유효성, 문제 목록, 수정 제안으로 판정을 구조화한다. [부록 H](https://arxiv.org/html/2607.16900#A8)

## 부록 I Agent

### AppWorld Agent 프롬프트

문서를 조회하고, 인증하고, 이전 반환값을 사용하며, Python 실행 결과를 다음 단계에 연결하도록 한다. 페이지 순회와 완료 API 사용도 명시한다.

### OfficeBench Agent 프롬프트

활성 앱을 전환한 뒤 JSON 행동을 하나씩 수행한다. 지정 작업 디렉터리 범위와 종료 규약이 포함된다. 같은 생성 원리라도 인터페이스별 행동 표현은 달라진다. [부록 I](https://arxiv.org/html/2607.16900#A9)

## 부록 J Trajectory 선별

### AppWorld Trajectory Judge 프롬프트

문서 확인, 요청 이해, 전략, 정보 흐름, 인자 근거, 반복 처리, 완료, 중복, 관련성을 검사한다. 평가자의 외부 상식 대신 Trajectory에 드러난 자료로 판단하도록 한다.

### OfficeBench Trajectory Judge 프롬프트

앱 전환, JSON 형식, 파일 경로와 부수 효과, 정답과 완료 신호, 허용 범위를 검사한다. 모사 관측에서 보이는 결과를 판정하므로 실제 파일 내용과 같은 실재 상태를 별도로 실행 검증하는 절차는 아니다. [부록 J](https://arxiv.org/html/2607.16900#A10)

## 부록 K 합성 애플리케이션 모음

### K.1 도메인 선택

사람이 넓은 기능 범주와 초기 앱 사례를 정하고 Gemini-2.5-Pro로 확장한다. 명세만으로 과제를 만든다는 설명을 전체 도메인 설계에도 사람이 전혀 관여하지 않았다는 뜻으로 읽으면 안 된다.

### K.2 API Schema 설계

AppWorld의 은행 앱 API를 구조 시범으로 제공해 인증·조회·생성·페이지·하위 자원 패턴을 학습 문맥에 넣는다.

#### 프롬프트 구조

도메인, 기능 Coverage, JSON 형식, 공통 규약, 시범 API를 제공한다. 원문의 축약 프롬프트에서 생략 표시한 세부는 복원하지 않는다.

#### 검증

필수 키, 인증 인자, 경로, HTTP 방식, 응답 구조 등의 규칙을 확인하고 실패하면 재생성한다.

#### Schema 구조

API 이름·경로·방식·설명·인자·응답 등을 공통 형태로 만든다. 보조 함수가 일관된 명세 생성을 돕는다.

#### 설계 규약

인증, 페이지, 타입 자리표시자, 제약 표현, 중첩 자원, 오류 응답을 통일한다. 앱 간 차이를 늘리면서 인터페이스의 불필요한 차이는 줄이는 구성이다.

### K.3 Schema 변환

AppWorld 형식으로 변환하고 추적용 Canary String(기억 여부 탐지용 표식)을 붙인다. 변환 실패에는 결정적 변환기를 대체 수단으로 사용한다.

### K.4 AppWorld 통합

명세에서 등록 정보, 모델, API stub(구현 자리표시자), 응답 타입 등을 생성한다. 이 등록·연결 코드의 존재는 학습 데이터 생성 시 실제 업무 백엔드를 실행했다는 뜻은 아니다. [부록 K](https://arxiv.org/html/2607.16900#A11)
