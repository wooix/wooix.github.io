## 초록

<strong>Program Synthesis(프로그램 합성)</strong>로 얻은 코드가 실제로 맞는지 판단할 때, 벤치마크의 테스트가 충분하지 않으면 잘못된 코드를 정답으로 셀 수 있다. EvalPlus는 기존 문제에 새로운 테스트 입력을 합성해 <strong>Functional Correctness(기능적 정확성)</strong> 평가를 강화하는 방법이다. 문제 설명으로 코드를 생성하는 모델을 새로 학습시키는 논문이 아니라, **그 모델을 평가하는 자료와 절차를 개선하는 논문**이다.

<strong>Large Language Model(대규모 언어 모델, LLM)</strong>로 의미 있는 초기 입력을 만들고, 자료형을 고려한 변형으로 입력 수를 늘린다. HumanEval의 164개 문제를 확장한 HumanEval+로 당시 26개 모델을 평가하자 기존 테스트에서 통과하던 코드 상당수가 실패하고, 일부 모델의 상대 순위도 달라졌다. 그러나 더 많은 테스트를 통과했다고 모든 가능한 입력에 대한 정확성이 증명되는 것은 아니다.

## 1. 서론

LLM은 함수 서명과 자연어 설명을 읽어 코드를 생성한다. 서로 전혀 다르게 작성된 코드가 같은 기능을 구현할 수 있으므로, 정답 코드와 문장이 얼마나 닮았는지를 재는 BLEU 같은 지표는 기능 평가에 적합하지 않다. 모든 입력에 대한 정확성을 일반적으로 증명하기도 어려워, 실용적인 벤치마크는 테스트 실행 결과에 의존한다.

이때 “평가 점수가 높다”는 결론은 테스트 자체의 적절성을 전제로 한다. 서론은 모델의 능력만 살피던 관점을 평가 자료의 결함으로 돌린다.

### 불충분한 테스트

기존 테스트는 수가 적고 단순해 경계 조건이나 복잡한 동작을 충분히 드러내지 못할 수 있다. Figure 1의 코드는 두 목록의 공통 원소를 중복 없이 정렬해 반환해야 한다. 중간 결과를 정렬했지만 마지막에 다시 `set`으로 바꾸므로 순서를 보존한다는 보장이 사라진다. 기존의 간단한 입력에서는 통과해도 다른 입력에서는 오류가 드러난다.

왼쪽은 테스트 입력, 가운데는 생성 코드, 오른쪽은 출력이다. 초록색은 기존 입력에서 기대와 맞는 경우이고, 붉은색은 추가 입력에서 [8, 1, 6]처럼 정렬되지 않은 결과가 나온 경우다. 핵심은 `sort()` 호출이 있다는 사실이 아니라 최종 반환까지 정렬 조건이 유지되는지다. 원문의 실행 예시이며, 모든 Python 환경에서 집합 순서가 같은 방식으로 나타난다는 주장은 아니다.


### 부정확한 문제 설명

허용 입력의 범위나 예외 처리가 자연어 설명에 충분히 적혀 있지 않으면, 모델이 합리적으로 해석한 구현과 테스트가 서로 다른 가정을 사용할 수 있다. 예를 들어 양의 정수만 허용하는지, 빈 입력을 받으면 어떻게 해야 하는지가 빠질 수 있다. 이 경우 테스트 실패를 곧바로 생성 코드의 오류라고 판단하면 평가가 부당해질 수 있다.

따라서 테스트를 많이 추가하는 일과 **어떤 입력이 유효한지 명시하는 일**이 함께 필요하다. 이 문제는 §2.3의 입력 계약으로 이어진다.

### 제안

EvalPlus는 기존의 문제·참조 구현·기본 입력을 받아 새로운 입력을 생성한다. 먼저 ChatGPT가 참조 구현과 예시 입력을 읽고 복잡하거나 어려운 입력, 경계 사례를 제안한다. 그런 다음 입력의 자료형을 고려한 변형으로 수를 확장한다.

생성 코드와 참조 구현을 같은 입력에서 실행하고 결과를 비교하는 <strong>Differential Testing(차등 테스트)</strong>을 판정 방법으로 쓴다. 테스트 실행량을 줄이고 싶으면 검출력을 유지하도록 대표 입력을 고르는 축소 단계도 적용한다. 참조 구현이 잘못되면 판정도 잘못될 수 있다는 점은 뒤의 실험에서 실제로 드러난다.

### 기여

#### 연구

테스트 부족이 코드 정확성을 과대평가하게 만들 수 있음을 여러 모델에서 조사한다. 한 모델의 약점을 찾는 것뿐 아니라 평가 벤치마크 자체를 다시 검토하는 연구 문제를 제시한다.

#### 방법

LLM 기반 입력 생성, 자료형을 고려한 입력 변형, 잘못된 입력을 걸러 내는 계약, 테스트 축소를 결합한다. 뒤의 절들은 입력을 늘리는 단계와 줄이는 단계가 어떻게 다른 목적을 갖는지 설명한다.

#### 결과

HumanEval+는 테스트 규모를 약 80배로 확장하고, HumanEval+-mini는 이를 다시 약 47배 줄이면서 실험한 모델에서 비슷한 오류 검출 효과를 보인다. 일부 코드 생성 모델의 순위가 바뀌었으며, 원래 정답으로 제공한 참조 구현에서도 결함을 발견했다. 이 배수는 테스트 **개수**에 관한 요약으로, 실행 시간이나 모든 모델에서의 검출력을 같은 비율로 보장하지 않는다.

## 2. 접근 방법

참조 구현은 두 역할을 한다. 먼저 ChatGPT가 유효한 입력 구조와 문제 기능을 이해하도록 돕고, 다음으로 생성 코드 출력이 맞는지 비교하는 기준이 된다. 이 때문에 참조 구현과 입력 계약의 신뢰성이 전체 평가의 기반이다.

### 2.1. 자동 테스트 입력 생성

#### ChatGPT를 이용한 초기 입력 생성

프롬프트는 참조 구현, 기존 테스트에서 무작위로 고른 입력 예시, 흥미로운 새 입력을 만들라는 지시로 구성한다. 그림에는 복잡한 입력·어려운 입력·경계 입력을 요구하는 세 방향이 제시된다. 함수가 회문 등 의미적 구조를 요구하면, 단순한 무작위 자료보다 LLM이 이런 제약을 갖춘 초기 입력을 만드는 데 유리할 수 있다.

하지만 생성 입력이 실제 조건을 지키는지는 따로 확인해야 한다. 입력 전제 조건에 어긋나는 것은 제거한다. 그렇지 않으면 애초에 정의되지 않은 동작에서 두 구현이 다르다는 이유로 오탐을 만들 수 있다. 또한 모든 입력을 대형 모델로 생성하면 호출 시간과 비용이 커지므로, 뒤 단계는 초기 입력을 재사용하는 방식이다.

#### 자료형을 고려한 입력 변형

<strong>Type-aware Mutation(자료형 인식 변형)</strong>은 입력 풀에서 한 입력을 무작위로 골라 자료형에 맞게 바꾼다. 새 입력이 계약을 만족하면 풀에 추가하고 다시 선택·변형을 반복한다. 숫자를 바꾸거나 목록 원소를 제거·복제하는 단순 연산뿐 아니라, 복합 자료의 내부 원소도 재귀적으로 바꾼다.

이전에 등장한 자료 조각을 모아 다시 사용하는 <strong>Ingredient Mechanism(구성 조각 재사용 방식)</strong>도 적용한다. 이는 의미적 제약을 어기는 입력 생성을 줄이려는 보완책이며, 자료형을 유지한다고 모든 의미 조건까지 유지되는 것은 아니다.

**Table 1. 입력 자료형별 기본 변형 — 전체 항목의 한국어 재구성.** ([원문](https://arxiv.org/html/2305.01210v3#S2.T1))

| 입력 자료형 | 기본 변형 |
| --- | --- |
| `int`, `float` | 값을 1 증가 또는 감소 |
| `bool` | 무작위 Boolean 값 반환 |
| `NoneType` | `None` 반환 |
| `str` | 부분 문자열 제거·반복·변형한 부분 문자열로 교체 |
| `List` | 무작위 원소 제거·반복, 내부 원소를 변형해 삽입·교체 |
| `Tuple` | 목록으로 바꾸어 변형한 뒤 다시 Tuple로 변환 |
| `Set` | 목록으로 바꾸어 변형한 뒤 다시 Set으로 변환 |
| `Dict` | 키·값 쌍 제거, 기존 값 변형, 변형한 키·값 쌍 삽입 |

이 표는 생성 가능한 입력 전체의 정의가 아니라 기본 연산 목록이다. 변형으로 나온 자료가 함수의 계약을 통과해야 다음 단계의 유효한 테스트 입력이 된다. 특히 순서나 고유성, 양수 제한 같은 의미 조건은 자료형 검사만으로 충분하지 않다.

### 2.2. 테스트 묶음 축소

입력이 많아지면 오류를 더 잘 찾을 수 있지만 모든 후보 코드에 모든 입력을 실행하는 비용도 늘어난다. <strong>Test-Suite Reduction(테스트 묶음 축소)</strong>은 기존 테스트가 충족하던 요구를 보존하는 더 작은 부분집합을 찾는 문제다.

원래 테스트 집합을 $\mathcal{T}$, 축소한 집합을 $\mathcal{T}_{red}$라고 하면, 원문 조건의 의미는 다음과 같다.

$$
\forall r\in\mathcal{R},\quad
\left(\exists t\in\mathcal{T}:t\text{가 }r\text{을 충족}\right)
\Rightarrow
\left(\exists t'\in\mathcal{T}_{red}:t'\text{가 }r\text{을 충족}\right)
$$

어떤 요구 $r$를 기존 테스트 중 하나가 충족했다면, 축소 후에도 그 요구를 충족하는 테스트가 남아 있어야 한다. 핵심은 테스트 개수 자체보다 **어떤 요구를 보존할 것인지**다. 저자들은 이를 <strong>Set Cover(집합 덮개)</strong> 문제로 보고 탐욕적인 알고리즘을 사용한다. 작은 대표 집합을 찾는 절차이며, 전역적으로 가장 작은 집합임을 증명했다고 설명하지 않는다.

#### 코드 실행 범위

<strong>Branch Coverage(분기 커버리지)</strong>를 사용해 전체 테스트가 실행했던 분기들을 축소 후에도 실행하게 한다. 서로 다른 입력들이 같은 분기를 지나면 일부를 줄일 수 있다. 하지만 분기를 실행했다는 것과 그 분기 안의 잘못된 계산을 발견했다는 것은 다르다.

#### 인공 결함 프로그램 검출

<strong>Mutation Testing(변이 테스트)</strong>은 참조 코드에 작은 오류 하나를 넣은 프로그램들을 만든다. 예를 들어 비교 연산자를 바꿔 경계에서 잘못 동작하게 하고, 그 결함을 검출하는 테스트를 남긴다. §2.1의 Mutation은 **입력을 변형**하지만 여기서는 **프로그램을 변형**한다는 차이가 있다.

축소의 목표는 전체 테스트가 잡던 인공 결함 집합을 유지하는 것이다. 인공 결함을 잘 잡는 것이 실제 오류 검출력의 유용한 근거가 될 수 있지만, 이 결함 생성 규칙에 없는 모든 실수를 다룬다는 보장은 없다.

#### LLM 생성 코드의 오류 검출

실제로 LLM이 만든 잘못된 코드 가운데 각 테스트가 실패시킨 코드를 기록하고, 그 오류 검출 집합을 보존한다. 새 평가 대상 모델의 결과를 미리 아는 것은 불가능하므로, 평가할 모델을 제외한 다른 모델들의 코드로 축소 기준을 만든다. 이를 <strong>Leave-one-out(하나를 제외하는 검증)</strong> 방식으로 평가한다.

이 방법은 이미 관찰된 실제 오류를 보존하는 데 직접적이지만, 새로운 모델만 만드는 오류 유형까지 완전히 보존한다고 가정할 수는 없다. 세 기준을 모두 결합한 축소도 비교하며, §3은 같은 평가 대상의 오류 기록을 사용하지 않고도 어느 정도 검출력이 유지되는지 살핀다.

### 2.3. 프로그램 입력 계약

<strong>Program Contract(프로그램 계약)</strong>를 `assert n > 0` 같은 코드 단언문으로 명시해 함수가 받을 수 있는 입력의 전제 조건을 정한다. 계약 밖의 입력에서 생긴 결과 차이는 사용자가 요구한 기능의 실패인지 분명하지 않으므로, 생성 과정에서 이런 입력을 걸러 낸다.

계약은 자연어 문제 설명을 보완하는 추가 명세로도 사용할 수 있다. 다만 계약을 만족한다는 사실은 **입력이 유효하다**는 뜻이지 출력이 맞다는 뜻은 아니다. 계약 자체가 사용자의 의도를 잘 반영하는지도 중요하다.

## 3. 평가

### 설정

HumanEval은 사람 손으로 작성한 Python 문제 164개를 제공한다. EvalPlus는 문제당 약 **30개 초기 입력**을 세 개의 프롬프트로 생성하고, 이를 바탕으로 **1시간 예산에서 추가 입력 1,000개를 생성**하는 설정을 사용한다. 164개 문제 중 **83개**에 수작업 계약을 부여한다. 즉, 완전히 사람 개입 없이 테스트 명세까지 만들어 낸 실험은 아니다.

참조 구현도 다시 구현하고 검사했다. 더 강한 테스트를 적용하려면 출력 비교의 기준이 먼저 신뢰할 수 있어야 하기 때문이다. 뒤에서는 원래 참조 구현에서 발견한 18개 결함을 분석한다.

평가는 <strong>pass@k(후보 k개 중 적어도 하나가 통과할 확률 지표)</strong>의 편향을 보정한 추정 방식을 사용한다. 각 모델·문제·온도에 대해 200개 코드를 샘플링하고, 온도 0.2·0.4·0.6·0.8에서 평가한다. $k=1,10,100$ 각각의 가장 좋은 값과 해당 온도를 보고한다. 따라서 표의 서로 다른 k열이 반드시 같은 생성 온도의 결과인 것은 아니다.

이와 별도로 <strong>Greedy Decoding(탐욕적 디코딩)</strong>으로 문제당 코드 하나를 생성한 통과율을 $\mathrm{pass@1}^{\star}$로 표시한다. 무작위 샘플링의 pass@1과 구분한다. 시간·비용 때문에 GPT-4는 Greedy Decoding만, ChatGPT는 Greedy Decoding과 온도 0.8 샘플링만 평가했다. GPT-4에 없는 샘플링 값을 추정해 채우지 않는다.

대부분의 모델·크기·k에서 테스트를 강화하면 점수가 낮아진다. 예를 들어 GPT-4의 Greedy 통과율은 **88.4→76.2%**, ChatGPT는 **73.2→63.4%**다. 표에 표시된 값을 빼면 각각 **12.2%p·9.8%p 감소**이며, 이 값은 원문 표를 이용한 단순 계산이다. 새 테스트가 이미 생성한 코드의 오류를 추가로 드러낸 것이므로, 평가 변경 때문에 모델 자체의 생성 능력이 갑자기 나빠졌다는 의미는 아니다.

원문 산문은 이 두 모델의 상대 감소율을 각각 13.1%·12.6%라고 쓰지만 Table 3의 표시값과 맞지 않는다. 따라서 여기서는 표의 전후 점수와 %p 차이를 중심으로 설명한다. 원문이 초록·결과에서 보고한 최대 상대 감소율도 %p와 다른 단위라는 점을 구분해야 한다.

순위도 바뀐다. Greedy 조건에서 HumanEval의 Phind-CodeLlama 34B는 71.3%, WizardCoder-CodeLlama 34B와 ChatGPT는 73.2%로, 두 공개 모델이 ChatGPT보다 높다고 할 수 없다. HumanEval+에서는 **67.1%·64.6%·63.4%**가 되어 두 공개 모델이 모두 ChatGPT보다 높다. 다만 이 순위 역전을 무작위 샘플링의 모든 k로 확대하지 않는다.

작은 k에서는 낮은 온도, 큰 k에서는 높은 온도가 좋은 경향도 관찰한다. 하지만 CodeGen-2B의 pass@10처럼 최적 온도가 0.8에서 0.2로 바뀌는 사례가 있다. 평가 입력의 엄격함과 생성 다양성 사이의 관계가 항상 일정한 것은 아니다.

Coverage는 분기 보존, Killed mutants는 인공 결함 검출 보존, Killed samples는 다른 LLM의 오류 코드 검출 보존, Full은 세 기준의 결합이다. 각 #tests는 기존 HumanEval 테스트를 포함한 문제당 평균 개수이고 점수는 Greedy 통과율(%)이다. Ref.의 base·+extra는 축소 전 비교값이다. 평가 대상 모델 자체의 오류 코드 기록은 선택 기준에서 제외했다.


문제당 평균 764.1개에서 16.1개로 줄인 HumanEval+-mini는 상당한 검출력을 유지한다. 그러나 **완전히 동일한 판정은 아니다**. GPT-4는 Full에서 78.0%, 전체 HumanEval+에서 76.2%로 차이가 남고, ChatGPT도 65.2%와 63.4%다. 이 맥락에서 통과율이 더 높게 남는다는 것은 일부 오류를 축소된 테스트가 추가로 놓쳤다는 뜻이다.

실험한 모델에서는 다른 LLM의 오류 코드 검출을 보존하는 기준이 가장 효과적이며, Killed samples와 Full의 통과율이 같은 행들이 나온다. 세 기준을 결합해도 이 표에서 더 많은 오류를 잡지 못하는 경우가 있지만, 저자들은 분기·인공 결함에 관한 추가 보존 조건 자체에도 의미가 있다고 설명한다. 이 조건을 모든 새로운 오류의 검출 보장으로 해석하지 않는다.

**원문 내부의 불일치:** Table 4 캡션은 전체 HumanEval+ 평균을 774.8개라고 쓰지만 Table 2와 본문의 설명은 764.1개다. 또한 Table 4 참조 열의 Vicuna-13B base 17.1%는 Table 3의 16.5%와, Vicuna-7B +extra 10.4%는 Table 3의 11.0%와 다르다. 표는 원문값을 보존했으며 이 차이를 임의로 합치거나 새 결과로 해석하지 않는다.

### 문제별 통과율 분포

전체 평균만 보면 어떤 유형에서 기존 테스트가 약했는지 가려질 수 있다. 저자들은 문제마다 모든 평가 모델이 생성한 코드의 평균 통과율을 계산해 비교한다. 추가 테스트는 어려운 문제뿐 아니라 여러 난도의 문제에서 기존에 통과했던 오류 코드를 찾는다.

가로축은 HumanEval 통과율이 낮은 순서로 정렬한 164개 문제이며 원래 문제 번호 순서가 아니다. 세로축은 모든 LLM 생성 표본의 평균 통과율(%)을 로그 눈금으로 표시한다. 옅은색은 HumanEval, 진한색은 HumanEval+다. 두 높이의 차이는 추가로 검출된 실패를 나타내지만 로그축의 시각적 간격을 그대로 %p 차이로 읽으면 안 된다.


두 수 더하기·문자열 길이처럼 간단한 문제는 생성과 수작업 테스트가 모두 상대적으로 쉽다. 반대로 여러 조건의 결합, 음수를 포함한 소수 판정, Tribonacci 같은 추론, 합리적인 입력 크기에서의 효율성 조건은 더 어려웠다. 이는 논문이 관찰한 과제별 차이이며 한 장의 그래프로 모든 오류 원인을 인과적으로 분리한 것은 아니다.

### HumanEval의 잘못된 참조 구현

저자들은 자신들이 다시 구현한 코드와 원래 참조 구현을 Differential Testing해 **18개 결함**, 즉 문제의 약 11%에서 문제를 찾았다. 분류는 경계 입력 미처리 **5개**, 잘못된 논리 **10개**, 성능 문제 **3개**다. 생성 코드뿐 아니라 정답 역할의 코드도 검토 대상이라는 점이 이 결과의 의미다.

Figure 4의 날짜 검사에서는 `and`가 `or`보다 먼저 결합된다. 월 조건과 일 조건을 의도대로 묶지 않으면 `day > 30`이 해당 월인지와 무관하게 적용될 수 있다. 그래서 12월 31일처럼 유효한 날짜도 잘못 거부한다.


<figure class="paper-figure" id="figure-4"><a href="/images/papers/liu-2023/figure-4.png" target="_blank" rel="noopener"><img src="/images/papers/liu-2023/figure-4.png" width="1384" height="280" alt="HumanEval #124의 참조 구현이 유효한 날짜를 거부하는 논리 오류." loading="lazy" /></a><figcaption>Figure 4. HumanEval #124의 참조 구현이 유효한 날짜를 거부하는 논리 오류. <a href="https://proceedings.neurips.cc/paper_files/paper/2023/file/43e9d647ccd3e4b7b5baab53f0368686-Paper-Conference.pdf#page=9">원문</a></figcaption></figure>

왼쪽 입력은 12-31-1999이고 가운데 두 조건문은 월 범위와 일 범위를 검사한다. 두 번째 조건의 `day > 30`이 괄호 없이 `or`로 붙어 있어 12월에도 참이 되고 False를 반환한다. 오른쪽 붉은 설명은 이 날짜가 유효함을 강조한다. 이 사례는 참조 구현을 사용했다는 사실만으로 판정이 옳아지는 것은 아님을 보여 준다.


기존 기본 입력은 이 오류를 드러내지 못했다. 다만 새 참조 구현을 다시 작성하고 테스트했다는 사실도 모든 입력에 대한 형식적 정확성 증명과는 다르다. 검증의 신뢰도는 입력 범위·참조 구현·출력 비교·실행 제한이 함께 정한다.

## 4. 관련 연구

### 코드용 LLM

코드 생성 외에도 프로그램 수정, 테스트 생성, 언어 간 코드 변환, 코드 요약에 LLM을 사용하는 연구를 정리한다. 이 논문은 생성 모델의 구조를 새로 제안하기보다, 다양한 코드 생성 모델을 평가하는 공통 절차의 신뢰도를 높이는 위치에 있다.

### LLM용 코드 벤치마크

HumanEval은 Python 문제 164개와 참조 구현·테스트를 제공한다. MBPP는 문제 974개에 보통 테스트 세 개를 제공하며, Spider·HumanEval-X·CodeContests·MultiPL-E 등은 다른 언어와 설정으로 범위를 넓힌다. GitHub 이슈와 저장소·테스트를 함께 사용하는 실제 소프트웨어 작업의 평가도 언급한다.

이 문헌 목록은 코드 과제가 다양하다는 배경이다. **이 논문의 EvalPlus 정량 실험은 HumanEval에 집중**하므로, 여기서 언급한 모든 벤치마크에서 같은 80배 확장이나 점수 하락을 검증한 것은 아니다.

### 자동 테스트 생성

전통적인 방법에는 무작위 입력이나 변형 입력을 넣는 방식, 소스 코드를 분석하는 방식, 분기 실행 정보를 되먹임으로 쓰는 방식이 있다. 의미적으로 제약된 입력을 동적 자료형 언어의 여러 문제에 맞춰 만드는 데 어려움이 있다는 것이 저자들의 문제의식이다.

EvalPlus는 참조 코드를 읽는 LLM으로 의미 있는 시작 입력을 만들고, 이후에는 자료형 기반 입력 변형으로 확장한다. 의미 이해가 필요한 초기 단계와 많은 입력을 만드는 단계를 나누어 결합한다는 점이 기존 방법과의 연결이다. 생성 단계 자체가 실행 분기 피드백으로 입력을 진화시키는 시스템이라고 혼동하지 않는다. 이 논문에서 Branch Coverage는 주로 테스트 축소의 보존 기준으로 사용한다.

## 5. 결론과 향후 연구

테스트 입력을 자동으로 강화하면 기존 벤치마크에서 정답으로 여겨졌던 오류 코드를 추가로 찾을 수 있고 모델 간 비교도 바뀔 수 있다. 의미를 고려한 LLM 입력 생성과 자료형 기반 변형을 결합하며, 선택적 축소로 평가 비용을 줄이는 것이 EvalPlus의 구성이다.

저자들은 후속 방향으로 MBPP 등 다른 벤치마크에 적용하는 일, Dafny 같은 형식 검증 도구나 변환 검증과 결합해 보장을 강화하는 일, 코드 보조 도구가 제안한 코드의 잠재적 결함을 개발자에게 알리는 일을 제안한다. 이들은 출판 시점의 전망이며 이 논문에서 모두 구현·검증한 결과가 아니다.

### 테스트 판정 기준

<strong>Test Oracle(테스트 판정 기준)</strong>은 모든 테스트 입력에서 생성 코드의 반환값이 기대 출력과 일치하고 합리적인 시간 안에 끝나는지 확인한다. 기본은 정확한 값 비교이며, 부동소수점 값은 HumanEval에 지정된 오차를 사용하고 별도 지정이 없으면 **절대 오차 $10^{-6}$**를 허용한다. 따라서 문자열 유사도나 모델의 답변 선호를 채점하는 절차가 아니다.

기존 HumanEval은 문제 하나의 전체 테스트에 3초 제한을 둔다. 입력 수가 크게 늘면 이 방식이 부당하게 엄격해질 수 있어, EvalPlus는 **각 테스트 입력마다** 다음 제한을 사용한다.

$$
t_{\mathrm{limit}}=\max(200\mathrm{ms},\;4t_{\mathrm{gt}})
$$

$t_{\mathrm{gt}}$는 해당 입력을 참조 구현으로 실행한 시간이다. 참조 구현보다 네 배 느린 시간을 허용하되, 매우 짧은 실행에서는 우연한 지연의 영향을 줄이려고 최소 200ms를 준다. 이는 문제별·입력별 실행 특성을 반영하는 실용적 판정 규칙이며 알고리즘의 점근적 복잡도나 실제 배포 환경의 성능을 증명하는 기준은 아니다.

결국 이 논문의 통과는 **허용된 입력, 검토된 참조 구현, 출력 허용 오차, 테스트별 시간 제한**이라는 조건 안에서 정의된다. 테스트 수를 늘리는 일만큼 이 조건들을 정확히 기록하는 일이 재현 가능한 코드 평가에 필요하다.
